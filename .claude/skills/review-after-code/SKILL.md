# Review after code

Every code change gets a review before it's committed: changes written in this session, by a helper agent, or by anyone else. Review the diff, fix what the review finds, then commit.

## Priorities, in this order

1. **Made for people.** Everything (code, scenes, structure, docs) is for the people who work on the project, not for an AI. It must look and work the way a Unity developer expects.
   - Scenes, prefabs, ScriptableObjects and settings are real committed assets, editable in the Inspector, never generated by editor menus or code.
   - No workarounds that exist only because Unity can't run in the cloud: no reflection or by-name type lookups to dodge the compile check, no editor generators, no test-only hacks in game code.
   - Inspector-facing fields are serialized and clearly named, with tooltips where they aren't obvious. Prefer configuring in the Inspector over hard-coding.
   - The folder structure follows normal Unity conventions (Scenes, Scripts, Prefabs, Data, Art, Editor, Tests), with nothing confusing.
   - Code reads as normal human-written Unity C#, with short, useful comments and no notes addressed to an AI.
   - Docs are written for people.
2. **Correctness.** Does it do what it's meant to, in every case, without crashing?
   - It compiles: run `Tools/compile-check/check.sh` (Unity 2021.3 reference assemblies; write C# 7.3).
   - Null references: Inspector fields left empty, `GetComponent` returning nothing, missing data rows.
   - Off-by-one errors, wrong units (days vs seconds, gold vs crates), integer division, rounding.
   - Cases not handled: empty lists, zero or negative values, a ship sinking mid-voyage, gold going negative, the last day of the mission.
   - State left inconsistent: cargo, gold or ownership changed in one place but not another; events fired twice or never.
   - Unity lifecycle and serialisation: Awake, OnEnable and Start ordering; event handlers unsubscribed in OnDisable or OnDestroy; renamed serialised fields losing their data (use `FormerlySerializedAs`); assets referenced by path or GUID.
   - Data: a missing or misspelled CSV row or column must fail loudly with a clear message, not silently use 0.
   - Randomness: game rules use a seeded random source so tests and bugs can be reproduced.
   - Blind spots of the compile check: it has no reference library for the Input System package, and only small stand-ins for TextMeshPro and UnityEditor. Code that uses those, or looks types up by name (`Type.GetType`, reflection), is not really checked. Review it by hand, flag it to the user as unverified, and prefer plain typed code.
   - Input: Active Input Handling is Both (`activeInputHandler: 2`), so anything that still reads the old `Input` class keeps working (the prototype camera already takes its Input System branch). Don't write new code against the old `Input` class. UI uses the Input System's `InputSystemUIInputModule` with the package's DefaultInputActions. New input code is normal typed Input System code (`using UnityEngine.InputSystem`). The compile check has no reference assembly for it, so keep that code out of the check or add a minimal stub, and flag it as unverified.
   - No assets looked up by name at runtime (`Resources.GetBuiltinResource`, `Shader.Find`, `GameObject.Find`). Fonts, materials and similar assets are serialized fields assigned in the Inspector. Empty fields are reported with a clear message naming the component, object and field.
3. **Pragmatism.** Is it the simplest thing that works for the vertical slice?
   - No speculative features, extra options or abstractions the slice doesn't need (see `Design/SliceScope.md` for what's in and what's parked).
   - Reuse what exists before adding something new.
   - Prefer a small, clear change over a clever one.
4. **Style.** Only after the above:
   - consistent names and folders
   - short comments where a rule isn't obvious
   - no dead code or leftover debug logging

## How to run the review

1. Run `Tools/compile-check/check.sh`. It must pass.
2. Run the built-in code review on the change (the `code-review` skill at high effort), or read the full diff yourself if that skill isn't available.
3. Sort findings by the priorities above.
   - Fix every made-for-people and correctness finding.
   - Fix pragmatism findings unless the fix costs more than it saves.
   - Fix style last, or leave it if the change is urgent.
4. Re-run the compile check after fixing.
5. Summarise for the user: what was found, what was fixed, what was left and why.

## Hand-written Unity YAML (scenes, prefabs, assets)

Unity can't open the file here, so check it by script before committing:

- Every GUID matches a real `.meta` in `Assets/` or a known package or built-in asset (uGUI scripts, the built-in font, material and shader assets).
- No fileID is duplicated within the file.
- Every component a script needs is present (`RequireComponent`, `GetComponent` calls, a `CanvasRenderer` beside each Image and Text, a `RectTransform` under a Canvas).
- Every serialized field name matches the script's `[SerializeField]` and public fields.
- Every reference (`{fileID: X}` without a guid) points at a document that exists in the file, and of the right type for the field. Parent and child links, and each GameObject's component list, match in both directions.
- Say plainly that the file still needs opening in Unity.

## Project rules that always apply

- No AI or assistant attribution anywhere: commit messages, trailers, authors, code comments or files.
- Commit as the repository's own git identity (`scarffy`), on the working branch.
- Content a person works with (scenes, prefabs, settings) is committed as real assets, never generated by an editor menu. Don't add editor menus that generate content.
- Unity behaviour can't be run here. Say plainly what was only compile-checked and what still needs a test in the Unity editor.
